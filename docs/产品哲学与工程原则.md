# FlyGo（飞狗）· 产品哲学与工程原则

> 本文档是 FlyGo 的"宪法"：所有代码、架构、UI 决策都必须符合这里的每一条。
> 与 AGENTS.md 冲突时，以本文档为准；发现冲突请先更新本文档再动手。

---

## 一、产品形态铁律：1 个 EXE + 1 个 APK

**对外交付物永远只有两个**：
- 电脑（Windows/macOS/Linux）：**一个 EXE/可执行文件**
- 手机（Android）：**一个 APK**
- 配置文件、数据文件、文档可作为补充，但不是交付主体。

**内部可以很复杂，外部必须极简。** 用户拿到软件 → 双击/安装 → 就能用。
所有 Docker、WSL、Syncthing、Tailscale、WebDAV/SMB 的复杂度，全部由软件内部消化，用户不可见。

## 二、Unix 哲学：拆小工具，能拼就拼，能复用就复用

1. **内部拆分成尽可能多的工具**，每个工具只做一件事，工具之间可重复组合。
2. **能复用就复用**：已有代码、已有二进制、已有服务，绝不重写。
3. **有工具用工具，有开源用开源**：优先拼现成开源项目（AGPL v3 无拼装障碍）。
4. **不依赖别人**：能自己造（或找到开源）就不依赖商业闭源服务。
5. **不能自己造就把别人包进来**：自研只发生在"无现成积木且是差异化核心"的地方（如 Windows 面板/托盘/daemon）。
6. **目标平台**：电脑三平台全适配（Windows/macOS/Linux，同一套代码各自编译）、手机 Android（APK）。
   iOS 暂缓评估：App Store 审核 + 无通用分发渠道，作为**远期可行性课题**（见下），不作为当前目标。

## 三、UI 原则：简洁易用

1. 移动端典型布局：顶部栏 + 右侧 ☰ 汉堡菜单，展开后菜单铺一列大按钮。
2. 用户不需要懂的细节（Syncthing 配对、端口转发、证书）一律隐藏，交给扫码/一键完成。
3. 任何操作三步内可达；任何状态一眼可读（绿=正常，红=异常，灰=未启用）。

## 四、按需启动（服务随用随开，不常驻空转）

**技术可以复杂，实现必须简单，效果是"打开就用"：**

- 软件常驻时只占 **十几~几十 MB 内存**，不常驻任何重服务。
- **服务在需要的时候才被打开**：用户点"媒体中心" → Docker + WSL 才启动 → Jellyfin 容器才拉起。
- 存储（SMB/WebDAV）在**被访问时**才挂载/启动。
- 具体用 SMB 还是 WebDAV，**按场景选最合适的**（见 §五），不盲目全开。
- 启动自检：软件启动时检查并修复 Tailscale 服务、portproxy、TCP 转发层、Docker engine、容器状态——"一打开就能用"（七步，见 `docs/tcpforward-design.md`）。

## 五、网络访问控制：面板内可配，不写死在防火墙里

**哪个网段能访问本机服务，必须在面板里由用户控制：**

- 面板提供访问控制页：可选项至少包括
  - 仅本机（127.0.0.1）
  - Tailscale 网段（100.64.0.0/10）
  - 局域网网段（如 192.168.1.0/24，用户可自定义网段）
  - 所有人（0.0.0.0/0，明确警告）
- 规则以命名前缀管理（`FlyGo-LAN-*` / `FlyGo-TS-*`），便于收紧。
- 防火墙规则的增删由面板调用提权脚本完成，规则状态在面板可见可回退。
- **安全默认值**：默认仅 Tailscale + 本机；放开局域网/全网是用户显式选择（当前 MVP 阶段为验证方便临时放开局域网）。

## 六、版本管理：年月日时间版本号

- 版本号 = **年月日时间**，格式 `YYYY.MM.DD-HHMM`，记录在项目根目录 `Version` 文件（唯一事实来源）。
- 构建脚本读取 `Version` 文件注入产物（EXE 版本资源 / APK versionName）。
- 每次发布新版本更新 `Version` 文件并提交。

## 七、iOS 评估（远期课题，不承诺）

- iOS 无法分发 APK，需原生 App（Swift）+ App Store 审核，成本高。
- 结论：**iOS 不作为当前目标平台**；若未来需要，评估 React Native / 现成开源 iOS 客户端拼装（如 FileBrowser 类 App 走 WebDAV/SMB 访问节点），与"有开源用开源"一致。
- 当前 iOS 用户可通过浏览器访问面板/服务（PWA），不阻塞。
