## 一、目标与范围

### 1.1 飞狗软件部分的目标

把用户各设备的数据**汇聚**到飞狗节点（多一份副本）、节点之间**互备**（再多一份副本）、数据**永远在用户自己手里**、随时可访问（Tailscale P2P 组网）——这三个动作全部由软件完成，是"飞狗卖的是永远可用这件事"的技术内核。

软件交付形态三件套：

| 形态 | 载体 | 一句话职责 |
|---|---|---|
| **节点软件（电脑端）** | FlyGoLegacy 面板（flygo.exe 单二进制）+ WSL2 Docker 栈 | 节点即产品主体：存储 + 连接 + 计算，全部落在这一层 |
| **汇聚客户端（手机端）** | 引导页 + 现成开源 App（Syncthing-Fork / Immich App / Sushitrain） | 手机只做"数据汇聚源"（上传不同步），MVP 期不承担节点职责 |
| **控制面（云端小后端）** | 单 VPS 上的 Rust 单二进制 + SQLite | 设备注册、激活码、订阅状态机、心跳、容量计量、管理后台——只管身份与订阅，不碰数据 |

### 1.2 产品骨架：四类同步链路

飞狗软件的产品骨架是四条同步链路，全部现有或新增组件围绕它们组织：

| 链路 | 对应 SKU 场景 | 副本效果 |
|---|---|---|
| ① 电脑 ↔ 外置硬盘 | 单机版（个人数据集合） | 源 1 份 + 节点 1 份 = **2 份** |
| ② 电脑 ↔ 手机 | 单机版（个人数据集合） | 手机数据汇聚到节点，**2 份** |
| ③ 手机 ↔ 手机 | 双保险版（家庭数据集合） | 全家照片经节点汇聚，**2 份以上** |
| ④ 电脑 ↔ 电脑 | 双保险版 / 三节点版 | 节点互备，**3 份以上** |

数据流主线：**各设备汇聚 → 节点内多副本（跨盘镜像）→ 节点间互备**。控制面只旁观元数据，不参与任何数据流转。

### 1.3 范围边界（只做软件，不做这些）

- **不做硬件**：二手手机采购、翻新、物流、备机池是运营侧，不在本计划内。
- **不做物流/换新执行**：换新工单只做到"控制面生成工单 + 诊断报告上传"，线下履约归运营。
- **不做支付与牌照**：支付回调只留接口（激活码由运营后台人工签发，支付链路后置）。
- **不自研同步引擎**：文件同步一律 Syncthing；相册备份一律 Immich；组网一律 Tailscale（官方控制面）。飞狗自研只做**整合层与编排层**（遵循项目哲学"有开源用开源，不以自造轮子为目标"）。
- **MVP 期手机不当真节点**：可行性分析结论——SMB 445 需 root 与"ROOT 不保"矛盾、手机无 Docker/转码、ROM 保活矩阵是持久战。手机只做汇聚客户端，手机真节点列为阶段三激进路线（前置评估门）。

### 2.2 分层职责与边界

| 层 | 职责 | 明确不做什么 |
|---|---|---|
| **节点软件（电脑端）** | 存储挂载、文件访问、容器计算、汇聚接收、互备执行、健康上报 | 不依赖控制面才能工作（控制面挂了，节点本地一切照常） |
| **汇聚客户端（手机端）** | 上传数据到节点（相册/文件），浏览节点文件 | 不承担同步回推（不同步）、不做节点服务、不做互备 |
| **控制面（云端）** | 身份（设备/用户）、激活码签发与校验、订阅状态机、心跳采集、容量计量、管理后台、配对信令中转 | 不中转文件、不接收数据内容、不介入 Syncthing/Tailscale 数据平面 |

### 2.3 关键数据流

```
汇聚：手机相册/电脑文档 → Tailscale 隧道 → 节点 E 盘汇聚目录（1 份）
     ↓
多副本：E 盘重要目录 → robocopy /MIR 镜像 → C 盘 Mirror 目录（2 份）
     ↓
互备：节点 A 数据目录 → Syncthing(send-receive, staggered 版本控制)
      → Tailscale P2P → 节点 B 数据目录（3 份，且带可回滚历史版本）
     ↓
恢复：节点损坏/换新 → 激活后从互备对端拉回（恢复进度页展示）
```

## 三、四类同步链路实现方案

### 链路 ①：电脑 ↔ 外置硬盘（单节点双副本）

- **组件清单**：alist/OpenList（5244，E 盘全挂，网页文件管理）· SMB（`NAS`→E:、`CROOT`→C:）· robocopy 跨盘镜像（`backup\sync-important-files.ps1`，`/MIR /XO /R:2 /W:3 /XJ`，托盘管家同步定时器每 600s 执行）· USB 外置盘守卫（弹出自动停 alist+同步，插回自动恢复）· 面板「同步」页。
- **流程**：用户在「同步」页把要双副本的目录放入 `E:\Sync_Important_Files`（或网页选择镜像源/目标）→ 定时器跑 robocopy → `C:\FlyGoLegacy\Mirror\...` 生成第二副本 → 页面展示最近一次镜像结果/失败项。
- **复用 vs 新建**：**几乎全复用**（镜像、守卫、定时器均已落地）。新建只有：镜像目录选择 UI + 镜像结果/健康展示（小）。
- **工作量**：小（1 周内）。

### 链路 ②：电脑 ↔ 手机（汇聚，上传不同步）

- **组件清单**：手机端 Tailscale App（组网）· Syncthing-Fork（相册/下载目录设为 **send-only**，只上传不接收删改）· 飞狗汇聚引导页（手机浏览器直达面板 `/gather` 页）· 面板 alist 文件页（手机浏览节点文件）· Immich App（照片备份，可选路径）。
- **流程**：装 Tailscale → 装 Syncthing-Fork → 打开引导页 → 输入节点 IP 与配对码（Syncthing device ID）→ 手机目录设为 send-only 指向节点汇聚目录 → 按引导完成保活设置（电池白名单/自启动/后台活动，按厂商弹对应路径）。
- **复用 vs 新建**：复用 Syncthing（已有，含多设备配对经验）、Tailscale、alist。新建：汇聚引导页（`/gather`，含分厂商保活设置清单）+ 配对码生成接口（中）。
- **关键设计**：**手机侧一律 send-only**——手机数据只进不出，节点永远不反向删除手机文件（防误删传播的根）。
- **工作量**：中（引导页 2 周 + 保活矩阵文档持续维护）。

### 链路 ③：手机 ↔ 手机（经节点汇聚，家庭场景）

- **组件清单**：每台家人手机装 Immich App（照片）或 Syncthing-Fork send-only（文件）→ 节点 Immich 四容器（2283）或 Syncthing 汇聚目录 → 面板「相册」页（Immich 内嵌）。
- **流程**：相册汇聚引导（见 4.5）→ 各手机扫码连节点 → 自动备份 → 每手机一个 Immich 用户/相册库（或 Syncthing 每设备一子目录）→ 节点成为全家照片汇聚点。
- **复用 vs 新建**：复用 Immich compose（已有四容器定义）、面板相册页（已有 iframe 内嵌 + 冷启动兜底）。新建：相册汇聚引导（扫码/内存检测/ML 开关，小-中）。
- **关键认知**：**手机↔手机不直连**——全部经节点中转汇聚，节点即"家庭照片汇聚点"。这正好兑现计划书场景 B"全家人的数据从四份各自孤立变成汇聚到一处"。
- **工作量**：小-中（2 周）。

### 链路 ④：电脑 ↔ 电脑（节点互备，双保险/三节点）

- **组件清单**：两台节点各跑 FlyGoLegacy 面板 + Syncthing + Tailscale · **互备编排模块**（一键配对/目录选择/staggered 版本控制/健康监控/恢复进度页，见 4.2）· 控制面配对信令中转（只转 device ID 与邀请码）。
- **流程**：两台节点都在控制面激活 → A 机面板「互备」页点"发起互备" → 生成 6 位邀请码 → B 机输入 → 控制面互换 Syncthing device ID → 两边 REST API 互加设备 → Tailscale 下 P2P 直连（22000 端口）→ 用户勾选互备目录 → 自动开启 staggered 版本控制（默认保留 10 个版本 / 7 天）→ 进入持续健康监控。
- **复用 vs 新建**：复用 Syncthing REST API（8384 已内网可达）、Tailscale P2P、面板。新建：互备编排模块（中）+ 恢复进度页（小）。
- **工作量**：中（3-4 周）。

## 四、新增模块设计

> 每个模块：做什么 / 技术选型 / 依赖 / 工作量 / 先后。

### 4.1 控制面 MVP（云端小后端）—— 全部 SKU 的前提，最先做

**做什么**（只做"身份 + 订阅"，不做数据平面）：
1. **设备注册**：节点首次启动生成 `device_uuid` + 本地密钥对 → `POST /v1/register` 注册 → 控制面下发 `device_id`。
2. **激活码**：运营在后台签发 8 位激活码（对应 SKU 与时长）→ 用户节点面板输入 → `POST /v1/activate` 绑定订阅（激活码只能绑定一次）。
3. **订阅状态机**：状态最小化——`trial(30天) → active(1年) → expiring(到期前30天标记) → expired`；续费 = 新激活码再激活；不做退款/转赠等复杂状态（运营人工处理）。**expired 只停互备与 Pro 服务，绝不停单机基础功能与已有数据访问**（不给用户制造数据损失风险，兑现"永远可用"）。
4. **心跳**：节点每 5 分钟 `POST /v1/heartbeat`，上报 `{device_id, version, disk_total, disk_used, services{...}, pair_status}`；控制面记录时间线，超 15 分钟无心跳标记离线。
5. **容量计量**：心跳内携带磁盘总量/已用/剩余，控制面累计展示配额与使用趋势（为容量保障运营提供数据）。
6. **管理后台**：用户列表 / 设备列表 / 订阅状态 / 心跳时间线 / 激活码签发与作废 / 换新工单入口（阶段三）。

**技术选型**：Rust + axum（与面板/webcli 同栈，团队全部经验可复用，单二进制静态编译、内存占用低）+ SQLite（rusqlite，单文件库、零运维）；HTTPS 用 Let's Encrypt（或 VPS 反代）；管理后台前端内嵌（复用面板 `include_str!` 单文件经验）。备选 Go（若未来招聘偏好 Go 再评估，本计划按 Rust 写）。
- API 设计（全部 JSON）：`POST /v1/register` · `POST /v1/activate` · `POST /v1/heartbeat` · `GET /v1/subscription/{device_id}` · `POST /v1/pair-invite`（互备信令）· `GET /admin/*`（后台，独立鉴权）。

**依赖**：单 VPS（2C2G 起步）+ 域名（或 Tailscale serve 免端口）。现有资产可复用：面板的 axum/单文件/凭证运行时读/`spawn_blocking` 经验。

**工作量**：大（4-6 周），拆两刀——第一刀注册+激活+心跳（2-3 周，先跑通激活闭环），第二刀订阅状态机+后台+计量（2-3 周）。

**先后**：**P0，全项目最先**。没有激活/订阅，任何 SKU 都无法计费上线。

### 4.2 互备编排（双保险版的技术核心）

**做什么**：
1. **一键配对**：面板「互备」页，A 机"发起互备"→ 控制面生成 6 位邀请码 → B 机输入 → 控制面互换 Syncthing device ID → 双方通过 Syncthing REST API 自动互加设备 → 连通性验证（Tailscale 下 TCP 22000）。
2. **目录选择**：列出候选数据目录（含已镜像目录），用户勾选互备范围；每目录策略默认 `send-receive` + **强制开启 staggered 版本控制**（`fsPathVersions`，默认保留 10 版本/7 天）。
3. **健康监控**：每 60s 轮询 Syncthing REST（`/rest/system/connections`）→ 显示对端在线/延迟/错误计数/未同步文件数；状态随心跳带上控制面，异常触发面板红点告警。
4. **恢复进度页**：节点换新/重装 → 激活后检测到"互备对存在" → 面板自动进入"从对端恢复"模式 → Syncthing 自动拉取，按目录显示进度（`/rest/db/status` 拉 need files/进度）+ 恢复完成校验（文件数对比）。

**技术选型**：Syncthing REST API（localhost:8384，已有）+ 控制面配对信令（只转邀请码与 device ID，不转数据）+ 面板新模块 `syncthing-pair.rs`（Rust，复用 axum 与 dockerctl 的模式）。

**依赖**：Syncthing（已有，含 staggered 配置经验）· 控制面（4.1）· 面板（已有）。

**工作量**：中（3-4 周）。

**先后**：P0（阶段一尾完成配对骨架）→ 阶段二作为主力功能完整落地。

### 4.3 安卓汇聚客户端（手机端）

**候选路线**：主路线 (a) 引导现成 App；(b) 改造开源 App 留评估位。

**(a) 引导现成 App —— 本计划主路线（MVP 执行）**：
- **飞狗汇聚引导页**（`/gather`，手机浏览器直达面板）：分步骤引导——① 装 Tailscale（扫码下载）② 装 Syncthing-Fork（F-Droid/GitHub，⚠️ 明确提示别装已停更的官方版）③ 输入节点 IP + 配对码 ④ 相册/下载目录设为 send-only ⑤ 按厂商弹保活设置路径（小米 HyperOS/华为 EMUI/OPPO ColorOS/荣耀 MagicOS 各一页：电池白名单、自启动、后台活动、锁屏保持）⑥ 验证页（显示最近同步时间/文件数）。
- **保活壳**：MVP 不做原生 App，用"引导页 + 用户按清单设置"完成保活；ROM 适配矩阵做成**持续维护的文档 + 引导页数据**（对应计划书"一键适配引导"的降级版——因为手机不再是节点，保活从"必须成功"降级为"尽力而为"）。
- **为什么选 (a)**：可行性分析结论——手机无 Docker/转码、445 需 root 与"ROOT 不保"矛盾、ROM 保活是持久战；手机只做汇聚源时，现成 App（Syncthing-Fork 有活跃维护 + 保活补丁、Immich App 成熟）完全够用。有开源用开源。

**(b) 改造开源 App —— 评估位（不在 MVP 范围）**：
- PlainApp 研究结论**待出**。评估通过后（打包 Syncthing 核心 + 预设配对 + 品牌引导 + 前台服务保活），可获得"飞狗品牌一键体验"，但代价是原生安卓开发 + 各 ROM 保活适配的持久战。
- **决策门**：付费用户 ≥ 100 或（a）路线转化率数据证明品牌壳值得做之前，**不做 (b)**。本计划按 (a) 为主写，留本节为 (b) 评估位。

**iOS 侧**：Immich App（照片备份到节点，成熟）；Sushitrain（文件同步，App Store 名 Synctrain；⚠️ 预期管理：iOS 后台受限，只能打开 App 时同步——引导页写明，不承诺实时）。

**依赖**：现有 USAGE.md 的手机 App 指引可作引导页内容底稿；Tailscale（已有）。

**工作量**：中（引导页 2 周 + ROM 矩阵持续维护）。

**先后**：P1（阶段二）。

### 4.4 应用商店（Pro 增值）

**做什么**：
1. **应用目录**：预置服务模板（Jellyfin / Navidrome / Immich / Vaultwarden / Home Assistant / qBittorrent / alist / Nextcloud 等，来自 docker-compose.yml 已验证的 28 服务）。
2. **一键部署**：点"安装"→ 模板渲染成 compose 片段（数据目录/端口参数化）→ 写入节点 compose → `docker compose up -d` → 完成后「打开」直达 UI。
3. **端口冲突检测**：安装前扫描已监听端口 + 已用 compose 端口（netstat 或 `TcpListener::bind` 探测）→ 冲突则提示并建议换端口（模板端口变量替换）。
4. **Pro 门控**：订阅状态 = active 且含 Pro（99 元/年许可证）才可用；应用商店入口按控制面订阅状态开关。
5. **卸载语义**：只停容器不删数据卷（防误删，符合"无必要不改变"原则）。

**技术选型**：面板 `dockerctl.rs` 扩展 + 服务模板 JSON（借鉴 HomeDash ③"预置 10 个带端口图标模板"：模板 = 名称/图标/端口/描述/compose 片段）+ 轻量字符串模板渲染（不引重型模板引擎）。

**依赖**：WSL2 dockerd（已有）· docker-compose（已有，compose 动态解析已有）· 控制面订阅状态（4.1）。

**工作量**：中（3-4 周）。

**先后**：P1（阶段二，与 4.5 相册引导并行）。

### 4.5 相册汇聚引导（家庭场景转化入口）

**做什么**：

**技术选型**：Immich compose（已有四容器）+ 面板相册页（已有 iframe 内嵌 + 冷启动兜底）+ Immich REST API。

**依赖**：Immich 四容器（已有，内存教训已记录在 todo.md）· 面板（已有）。

**工作量**：小-中（2 周）。

**先后**：P1（阶段二）。

### 4.6 面板 v2（HomeDash 借鉴落地，节点软件的门面）

**做什么**：
1. **服务卡片墙 + 三色连通性检测**（HomeDash ①）：总览页升级为卡片墙——所有服务入口卡片，每卡片带连通状态灯；**并发 TCP ping**（tokio 并发探测各服务端口）：<200ms 绿 / <1000ms 黄 / 超时红；服务清单从 docker-compose 动态解析（已有）+ 用户自定义模板卡片。
2. **WS 按需推送**（HomeDash ②）：状态采集改 WebSocket 推送——`/ws/status` 1s ticker；**无客户端连接时完全不采集**（省 PowerShell 调用与 CPU）；有客户端才启动采集循环；采集沿用 `spawn_blocking` 经验。
3. **宿主级监控页**（HomeDash ⑧）：在现有 SMART/温度基础上补齐——GPU 利用率/温度（Windows 无标准 WMI，评估桥接 LibreHardwareMonitor，todo.md 已探明无现成 exporter 需自行桥接；先用可用的 WMI GPU 计数）、网速（`Get-NetAdapterStatistics` 两次采样差值）、CPU 温度（已有 MSAcpi 主板热区）。
4. **服务模板一键导入**（HomeDash ③）：用户自定义服务入口（名称/端口/图标/URL），存本地 JSON。
5. **反面教训落地**（HomeDash 反面清单逐一对照）：
   - 零鉴权 → 面板加登录层（复用 webcli 0909 门票经验，扩展为面板级 HttpOnly cookie 登录，后台管理页更强口令）；
   - 明文密码 → 保持现有"密钥运行时读 + gitignore"模型（term_token.env / alist_pass.txt 模式），新模块一律照此；
   - CDN 依赖 → 前端全部 `include_str!` 内嵌单文件（已有，保持）；
   - CLI 文本解析 → 新采集一律结构化输出（JSON），避免解析 PowerShell 文本。

**技术选型**：Rust axum + tokio-tungstenite（已有 WebSocket 反代经验）+ 前端 MPA 按页加载 JS（HomeDash ⑨：页面级 JS 文件组织，替代单文件全量加载）。

**依赖**：面板全部（托盘管家 / dockerctl / /api/system / webcli）。

**工作量**：大（4-6 周），可分刀——第一刀卡片墙+三色检测+WS 按需（2-3 周），第二刀宿主监控+登录层+模板（2-3 周）。

**先后**：P0（阶段一，与控制面并行）。

## 七、风险与对策表

| # | 风险 | 软件对策 |
|---|---|---|
| 1 | **Android 端风险**（ROM 杀后台 / 版本碎片化 / 无 Docker / 445 需 root）——最大技术风险 | 手机只做汇聚客户端（send-only，上传不同步），不当节点；汇聚引导页内置"分厂商保活设置路径"清单（小米/华为/OPPO/荣耀各一页）并做**预期管理**（明确"手机不是服务器，按需上传即可"）；手机真节点整体移出 MVP，列阶段三评估门；不承诺手机 7×24 在线 |
| 2 | **双向同步误删传播**——第二技术风险 | 互备目录**强制 staggered 版本控制**（默认 10 版/7 天，误删可回滚）；手机侧一律 send-only（根上杜绝反向删手机）；汇聚目录手机侧永不 send-receive；互备目录删除操作前告警确认；恢复演练纳入阶段二验收（见 M6） |
| 3 | **遥测隐私边界**（"数据在自己手里"承诺被遥测破坏） | 控制面**只收元数据**（device_id/版本/磁盘用量/服务健康/互备状态），不收文件名/路径/内容；数据平面与控制面物理分离（Syncthing/Tailscale P2P 直连不经控制面）；面板提供遥测开关（关闭后仅保留订阅校验心跳）；用户协议写明"飞狗不经手用户数据"（呼应计划书 6.4） |
| 4 | **换新恢复耗时**（HaaS 承诺"换新后数据恢复"） | 恢复进度页（按目录显示 Syncthing 拉取进度/剩余时间）；关键目录优先策略（先笔记/相册后媒体大目录）；控制面设备迁移流程（旧机注销→新机注册→自动指回互备对）；恢复演练列入阶段二/三验收 |
| 5 | **单点控制面故障**（云端小后端挂了） | **节点自治设计**：控制面只做身份/订阅/信令，不介入数据平面——控制面不可达时节点本地同步/互备/文件访问全部照常；心跳失败不惩罚（本地降级继续，恢复后补报）；控制面 SQLite 定期备份 + 无状态化（可整体迁移 VPS）；管理后台只读降级 |
| 6 | 订阅状态机复杂度失控 | 状态最小化（trial/active/expiring/expired 四态）；续费=新激活码；复杂场景（退款/转赠/改 SKU）运营人工处理，不进状态机 |
| 7 | 应用商店端口/镜像故障 | 端口冲突检测前置（安装前扫描）；国内镜像源默认（docker 镜像走国内加速）；模板安装失败可回滚（只停不删） |

## 九、与飞狗计划书 v5.0 的差异说明

> 技术计划对商业计划书技术假设的修正。计划书是商业愿景，本文是落地现实；修正不改变"汇聚多副本、永远可用、数据自控"的目标，只改技术路径。

| # | 计划书假设（v5.0） | 本技术计划修正 | 原因（可行性分析结论） |
|---|---|---|---|
| 1 | 飞狗节点 = 闲置手机（1TB UFS），手机锁屏常驻做服务器 | **手机降级为"汇聚客户端"（上传不同步）；节点 = 电脑（Windows，即 FlyGoLegacy 面板）**；手机真节点列阶段三评估门 | SMB 445 需 root 与"ROOT 不保"矛盾；手机无 Docker/转码；ROM 保活是持久战；电脑节点软件已做出八成，70%+ 可复用 |
